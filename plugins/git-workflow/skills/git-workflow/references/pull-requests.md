# Pull Requests

## The Description Is Derived from the Commits

Write the PR body from `git log <base>..HEAD`, not from `git diff`. Two reasons:

- **The diff answers "what changed"; GitHub already shows that.** The commit range answers "in what steps, and why," which is the part only the author has.
- **If the log will not yield a description, the history is the problem.** A branch whose log reads `wip`, `fix`, `more fixes`, `actually fix it` cannot produce a good PR body. Clean the history first (`/git-workflow:tidy-history`), then write the description.

```bash
BASE=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null || echo origin/main)
git log "$BASE..HEAD" --format='%h %s%n%b'
git diff --stat "$BASE...HEAD"      # three dots: changes on the branch only
```

Note the three-dot form for the diff. `git diff base..HEAD` shows the difference between two tips, which includes everything that landed on the base since branching. `base...HEAD` shows only what the branch itself did — that is what the PR represents.

## Anatomy

```markdown
## What

One or two sentences. The problem, and what this does about it.

## Why

The context that is not in the code: the incident, the ticket, the
constraint. What was rejected and why, if a reviewer might wonder.

## How to review

Where to start, what deserves scrutiny, what is mechanical. On a large
change this is the highest-value section in the whole description.

## Verification

What was run and what it showed. Not "tests pass" — which tests, and
what they now cover that they didn't.

## Notes

Follow-ups deliberately excluded, migration steps, feature-flag state,
anything that must happen at deploy time.
```

Adapt to the repository's `.github/PULL_REQUEST_TEMPLATE.md` when one exists — **check for it first** and fill in its sections rather than substituting this structure.

What not to include: a file-by-file enumeration (the Files tab exists), a restatement of the diff, or a summary generated by reading the code rather than the intent.

Link issues in the body with `Fixes #123` when the PR closes them — GitHub closes them automatically on merge, and only from the PR body or a commit message, not from a comment.

## Size

Review effectiveness collapses as changes grow, and this is measured rather than folklore. SmartBear's study of Cisco's review process — 2,500 reviews covering 3.2 million lines by 50 developers — found that the ability to find defects drops off beyond **400 lines per review**, that a 200–400 line review over 60–90 minutes yields 70–90% defect discovery, and that defect density falls sharply once reviewers exceed **500 lines per hour**. Past those thresholds reviewers skim, and approvals become rubber stamps. (Citation and caveats: `sources.md`.)

The practical rule: **if a PR cannot be reviewed carefully in under an hour, split it.**

Ways to split that actually work:

- Mechanical changes (rename, format, move) in their own PR, merged first. These are large and trivial; mixing them with logic hides the logic.
- Schema/interface first, implementation second.
- Add the new path behind a flag, switch over, delete the old path — three PRs.
- Stacked branches when the pieces genuinely depend on each other.

When a PR must be large — a generated-code update, a dependency migration — say so in the description and point the reviewer at the handful of files that are not mechanical.

## The `gh` Command Set

```bash
# Open a PR (--fill uses the commits for title and body)
gh pr create --base main --title "feat(api): add cursor pagination" --body-file /tmp/pr-body.md
gh pr create --draft ...                       # not ready for review
gh pr create --reviewer alice,bob --assignee @me --label backend

# Inspect
gh pr status
gh pr view --json title,body,url,state,reviewDecision,mergeable
gh pr diff
gh pr checks --watch                           # block until CI reports

# Iterate
gh pr edit --body-file /tmp/pr-body.md
gh pr ready                                    # draft → ready for review
gh pr comment --body "..."

# Merge
gh pr merge --squash --delete-branch
gh pr merge --auto --squash                    # merge when checks pass
```

Prefer `--body-file` over `--body` for anything multi-line: shell quoting mangles markdown, and on Windows the difference between shells makes inline bodies genuinely unreliable.

Authentication: `gh auth status`. If it fails, tell the user to run `gh auth login` themselves — it is interactive and cannot be driven from here.

If `gh` is absent, push the branch and give the user the compare URL: `https://github.com/<owner>/<repo>/compare/<base>...<branch>?expand=1`.

## Attribution

PR bodies keep the standard footer:

```
🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

Commit messages do **not** carry an AI-attribution trailer. This split is deliberate: the PR is a piece of communication where provenance is useful context for a reviewer; the commit log is a permanent technical record where the trailer is noise on every line of `git log`.

## Merge Strategy and Commit Quality

The repository's merge strategy determines whether the branch's commits matter permanently:

| Strategy | What lands on `main` | Implication |
|---|---|---|
| **Squash** | One commit; PR title becomes its subject | Branch commits are review scaffolding only. **The PR title must be a valid Conventional Commit subject.** Check the generated body before merging |
| **Rebase** | Every commit, replayed | Every subject is permanent. Clean the history before merging |
| **Merge commit** | Every commit, plus a merge commit | Same as rebase, and `main` is non-linear |

Detect it: `gh api repos/{owner}/{repo} --jq '{squash: .allow_squash_merge, rebase: .allow_rebase_merge, merge: .allow_merge_commit}'`, or look at whether `git log --merges origin/main` is empty.

Under squash merge, spending an hour perfecting branch commit messages is wasted; under rebase merge, skipping it puts noise in `main` forever.

## Responding to Review Feedback

**Add new commits during review. Do not force-push.**

Force-pushing mid-review outdates every inline comment and can hide reviewer context in the GitHub UI, forcing them to restart. Push `fix(review): ...` or `fixup!` commits instead, so the reviewer can read just what changed since they last looked.

If the repository squash-merges, those extra commits vanish on merge and cost nothing. If it does not, collapse them with `--autosquash` **after** the review is approved and say so in a comment before pushing.

Reply to each thread as it is addressed, and let the reviewer resolve their own threads — resolving your own removes their ability to check the fix.

```bash
gh pr view --json reviews,comments
gh api repos/{owner}/{repo}/pulls/{number}/comments --jq '.[] | {path, line, body}'
```

## Before Pushing

Preflight, in this order — each step is cheap relative to the one after it:

1. **Secrets and junk.** Scan the outgoing commits, not just the working tree:
   ```bash
   git diff "$BASE...HEAD" | grep -nEi '(api[_-]?key|secret|password|token|BEGIN [A-Z ]*PRIVATE KEY|xox[baprs]-|gh[pousr]_[A-Za-z0-9]{36})'
   git diff --stat "$BASE...HEAD" | tail -1
   git log "$BASE..HEAD" --name-only --format= | sort -u
   ```
   Look for `.env`, credentials, large binaries, `node_modules`, build output, and editor files. A hit **blocks the push** until resolved — see `recovery.md`, and note that removing a pushed secret requires rotating it regardless.

2. **Base currency.** `git fetch origin && git log --oneline HEAD..$BASE`. If the base has moved, rebase (or merge) before opening, so the PR is not stale on arrival and CI runs against something current.

3. **Tests and linter.** Detect the project's commands from `package.json` scripts, `Makefile`, `*.csproj`, `pyproject.toml`, or the CI workflow, and run them. Report failures and **ask before pushing anyway** — sometimes a known-red test is expected, and that is the user's call, not a reason to silently skip the check.

Then push and open:

```bash
git push -u origin "$(git branch --show-current)"
gh pr create --base "${BASE#origin/}" --title "..." --body-file /tmp/pr-body.md
```
